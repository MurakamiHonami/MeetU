# ADR-001: システムアーキテクチャと技術選定

## Background

本システムでは、通常のユーザー・投稿管理に加えて、複数ユーザー間でのN:N交換を実現する必要がある。

N:N交換では、単純なCRUDだけではなく、交換条件の判定やマッチングなどの複雑なビジネスロジックを扱う必要がある。

また、可能な限りCloudflareのサービス内でシステムを構成し、インフラストラクチャの複雑性を抑える。

## Decision

### 言語

TypeScriptを採用する。

Cloudflare Workersを中心とした構成とし、フロントエンド・バックエンドをTypeScriptで統一することで、Cloudflare上で一貫した開発環境を構築する。

N:N交換のマッチング処理については、処理量が増大した場合にTypeScriptでは性能上の問題が発生する可能性がある。

その場合は、マッチング処理をRustで実装し、別の計算基盤へ分離することを検討する。

### データベース

#### D1

ユーザー、投稿、交換情報などの主要な永続データをD1で管理する。

Cloudflare Workersとの統合が容易であり、システム全体をCloudflare内で構成できるため採用する。

#### KV

トレンド情報など、読み取り頻度が高く、多少の陳腐化を許容できるデータを保存する。

トレンド情報はリクエストごとに集計するのではなく、Cron Triggerから定期的に集計処理を実行し、その結果をKVに保存する。

#### R2

投稿画像やDMの添付ファイルなど、オブジェクトデータを保存する。

### ソフトウェアアーキテクチャ

#### Domain-Driven Design

DDDを採用する。

特にN:N交換では、交換条件、マッチング、交換成立などの複雑なビジネスルールを扱う必要がある。

これらのルールをドメインモデルとして明示的に表現し、UIやデータベースなどの技術的詳細から分離する。

#### Clean Architecture

Clean Architectureを採用し、ドメインロジックがD1などの具体的なインフラストラクチャに直接依存しない構成とする。

これにより、ビジネスロジックをDBやフレームワークから独立してテストできるようにする。

## Consequences

### Positive

- Cloudflareを中心としたシンプルなインフラ構成になる
- TypeScriptでフロントエンドとバックエンドを統一できる
- N:N交換のビジネスロジックをドメインモデルとして管理できる
- DBやCloudflare APIへの依存を分離することで、ドメインロジックをテストしやすくなる
- トレンド集計をキャッシュすることで、通常のリクエストで集計処理を実行する必要がなくなる

### Negative

- DDD + Clean Architectureによって、単純なCRUDと比較して実装量が増える
- D1/KV/R2などCloudflare固有サービスへの依存が発生する
- N:N交換の処理量が増大した場合、マッチング処理を別サービスへ分離する必要が生じる可能性がある
