# ADR-005: 画像からのタグ推定と、タグ検索のベクトル化

## Status

Accepted（フェーズ1のみ実装済み。フェーズ2以降は未着手）

## Context

MeetU のマッチングは、カードに付与された**タグの一致数**を中核に据えている（`MatchingEngine.satisfies()` が `minMatchCount` と `requiredTags` で判定し、`CycleFinder` もこの判定を辺の条件として再利用する）。したがってタグの品質と網羅性が、マッチングの精度をそのまま左右する。

しかしタグの入力はユーザーの手作業に依存しており、以下の課題があった。

- グッズ写真は撮れても、「作品名・キャラ名・アイテム種別」を毎回正確に言語化するのは負担が大きい
- 表記が人によってぶれる（「五条悟」「五条」「ごじょう」）
- 検索側も同じ表記を打たないとヒットしない。`ITagRepository.suggest()` は前方一致で、`TagNormalizer` の正規化（NFKC・記号除去）で吸収できる範囲を超えたゆれには対応できない

「特定のグッズを検索できるようにしたい」という要求に対し、当初は**類似画像のベクトル検索**を検討した。調査の結果、この方向は目的に合わないと判断した。以下にその根拠を記す。

### 調査1: Workers AI に画像埋め込みモデルが存在しない

[Workers AI のモデル一覧](https://developers.cloudflare.com/workers-ai/models/)を確認したところ、画像を扱うモデルは**画像分類（`resnet-50`）とビジョンLLM（`llava-1.5-7b-hf`、`llama-3.2-11b-vision-instruct` 等）のみ**で、CLIP のような画像埋め込みモデルは提供されていない。埋め込みモデルはすべてテキスト用である。

| 種別 | 提供状況 |
|---|---|
| テキスト埋め込み | `bge-small-en-v1.5`(384次元) / `bge-base-en-v1.5`(768) / `bge-large-en-v1.5`(1024) / `bge-m3` / `plamo-embedding-1b`（日本語特化）等 |
| 画像埋め込み（CLIP 等） | **提供なし** |
| 画像分類 | `resnet-50`（出力スキーマがドキュメントに未掲載。特徴ベクトルが取得できるかは未検証） |

このため「画像→ベクトル」を Cloudflare 内で完結させるには、Workers 上での ONNX 推論か、Containers での CPU 推論のいずれかを自前で用意する必要がある。

| | Workers 内で推論 | Containers で推論 |
|---|---|---|
| メモリ | **128 MB**（JSヒープ + WASM 合計） | `standard-1` で 4 GiB |
| バンドル上限 | 非圧縮 **64 MiB** | イメージ制限は緩い |
| 画像デコード | Canvas/Image API が無く、WASM デコーダを自前で用意する必要がある | PIL 等で素直に処理可能 |
| コールドスタート | 実質なし（モデル初期化は必要） | **2〜3 秒** |
| 成熟度 | GA | **ベータ**（SLA なし・オートスケール無し） |

### 調査2: そもそも画像埋め込みは目的に合わない

より本質的な問題として、**画像埋め込みが返す「類似」と、MeetU が必要とする「同定」がずれている**。

グッズの特定は「どの作品の・誰の・何のグッズか」という**記号の一致**で決まる。一方 CLIP 系の画像埋め込みが返すのは「見た目の近さ」であり、この用途では次の誤りを生む。

- 同じ型のアクリルスタンドは、**キャラクターが違ってもベクトルが近い**（＝別商品を同一視する）
- 同じグッズでも、**背景や光量が違うとベクトルが離れる**（＝同一商品を見逃す）

対してビジョンLLMは、画像から「プロセカ / 天馬司 / アクスタ」という**記号そのもの**を抽出できる。抽出された記号は既存のタグ一致マッチングにそのまま流し込めるため、`MatchingEngine` にも `CycleFinder` にも変更が要らない。

したがって、**画像は埋め込みではなくタグへ変換するのが正しい**と結論づけた。

### 調査3: 残る課題は表記ゆれであり、それはテキストの問題

画像→タグ推定を導入しても、「五条のアクスタ」で検索したときに「五条悟」「アクリルスタンド」で登録されたカードがヒットしない問題は残る。これは**画像ではなくテキストの意味的な近さ**の問題であり、テキスト埋め込みで解ける。テキスト埋め込みは Workers AI 内で完結し、Containers も CPU 推論も不要である。

## Decision

### フェーズ1（実装済み）: ビジョンLLM によるタグ推定

画像からタグ候補を推定し、**ユーザーが確認・編集したうえで**カードに付与する。

- モデル: `@cf/qwen/qwen3.8-27b`（`TagVisionService`）。キャラ名が不明なときは Cloudflare Web Search をツールとして使い、公式の日本語名を補う
- 出力は JSON に限定し、カテゴリを `work` / `character` / `item` / `event` / `area` / `trade` / `other` に制約する。タグ名は日本語の表示名で返させる
- 推定結果は**候補**であり、自動確定しない。LLM の誤りがそのままカードに載ることを防ぐため、必ずユーザーの確認を挟む

**同期実行を維持する。** タグ推定を Queue で非同期化する案も検討したが、ユーザーが登録画面でタグを確認・編集できることが品質の前提であるため、UI に結果を返す必要がある。非同期化するのは後述のベクトル生成のみに留める。

#### 待ち時間を体感させないための UI 設計

ビジョンモデルは相応の時間がかかるため、待ち時間を操作の妨げにしない作りにする。

1. **推定中もフォーム操作を止めない。** 写真選択ボタンの `disabled` を外し、推定中でも写真を差し替えられるようにする
2. **結果は後から差し込む。** `setTags` / `setTitle` を関数形（`prev => ...`）で呼び、`await` をまたいで古い状態を掴まないようにする。これを怠ると、推定を待つ間にユーザーが手入力したタグが結果で上書きされて消える
3. **競合した推定は打ち切る。** `AbortController` を `useRef` に保持し、新しい写真が選ばれたら前のリクエストを `abort()` する。応答時間はばらつくため、後から投げた要求が先に返ることがあり、対策しないと「画面には写真Bが出ているのにタグは写真Aのもの」という状態になる
4. **判定は `try` / `catch` / `finally` の3箇所すべてに置く。** `catch` に無いと古い失敗が新しい画面にエラーとして残り、`finally` に無いと古い要求が新しい推定のスピナーを消してしまう
5. **進行状況は控えめに示す。** タグ欄に「AIが写真を読み取り中…」を表示する（`role="status"`、`prefers-reduced-motion` で点滅を停止）

### フェーズ2（未着手）: タグのベクトル検索

表記ゆれ・同義語への対応として Vectorize を導入する。**カードではなくタグを埋め込む。**

```
[登録] 画像 → LLM → タグ推定（フェーズ1・変更なし）
                      ↓
       タグ作成時 → テキスト埋め込み → Vectorize（tagId をキーに）

[検索] クエリ文字列
         ├─ 前方一致（D1）          … 確実な一致を拾う
         └─ ベクトル近傍（Vectorize） … 表記ゆれ・同義語を拾う
              ↓ マージ
            タグ候補 → 既存のタグ一致マッチング（変更なし）
```

#### 埋め込み対象をタグに限定する理由

| | カードを埋め込む | **タグを埋め込む（採用）** |
|---|---|---|
| ベクトル数 | カード数に比例して増え続ける | **語彙数**。タグは収束するため頭打ちになる |
| 埋め込みの実行頻度 | カード登録のたび | **新規タグが出たときだけ** |
| 入力トークン数 | タイトル + 説明文 + タグ | タグ名のみ（短く安価） |
| 既存マッチングとの整合 | 取れない（後述） | **変更不要** |

#### 適用範囲を「入口」に限定する理由

ベクトルを使うのは次の2箇所に限る。

1. **検索の名寄せ**: `ITagRepository.suggest()` の内部を「前方一致 + ベクトル近傍」のハイブリッドにする。インターフェースは変えないため呼び出し側に影響しない
2. **タグ登録時のサジェスト**: 新規タグが既存タグと十分近ければ既存タグを提示し、同じ `tagId` に寄せる

**マッチング本体（`MatchingEngine` / `CycleFinder`）には持ち込まない。** 理由は3つある。

- 現行の中核は「タグが `minMatchCount` 件以上一致」という**離散的な数え上げ**である。ベクトル類似は連続値であり、「0.87件一致」を定義できない
- 「アクリルスタンド」と「缶バッジ」のような**同カテゴリの別物**は意味的に近い。閾値で一致とみなすと誤マッチが増える
- 名寄せをデータ側（同一 `tagId` への集約）で解決すれば、`minMatchCount`・`requiredTags`・共起拡張のいずれもそのまま正しく機能する

#### 実装上の制約（着手前に確定させるもの）

[Vectorize の仕様](https://developers.cloudflare.com/vectorize/)には、後から変更できない項目がある。

| 項目 | 内容 |
|---|---|
| 次元・距離メトリック | **インデックス作成後に変更不可**。モデルを確定し、出力次元を実測してから作成する |
| メトリック | テキスト埋め込みのため `cosine` を選ぶ |
| メタデータインデックス | **ベクトル投入前**に作成が必要（後から作っても既存ベクトルには遡及しない） |
| インデックス済み文字列メタデータ | 64 バイトまで |
| 書き込みの反映 | 5〜10 秒の遅延。新規タグが即座に検索へ出ない点は許容する |
| 1インデックスあたり上限 | ベクトル 10,000,000 件 / 最大 1,536 次元 |

モデルは日本語特化の `@cf/pfnet/plamo-embedding-1b` を第一候補とする。ただし**出力次元が公式ドキュメントに記載されていない**ため、インデックス作成前に一度実行して実測する必要がある。多言語対応が必要になった場合は `bge-m3` を代替とする。

### タグ数の上限（1カードあたり 10 個）

`MAX_TAGS_PER_CARD = 10` を、上限の**目的**とともに定数として一元管理する。

**上限を設ける目的**

1. **候補評価の量を抑える。** 候補抽出（`ICardRepository.findCardTagHits`）はタグ ID の `IN` 句で引くため、タグが増えるほどヒット行が増え、後段で `MatchingEngine.satisfies()` を評価する対象も比例して増える
2. **タグ盛りによる露出操作を防ぐ。** 上限が無いと、無関係なタグを大量に付けたカードほど検索とマッチの両方に引っかかりやすくなり、公平でなくなる

**10 という値について**

この具体値に理論的な裏付けはなく、**運用上の初期値**である。画像からの推定は `TagVisionService` の `MAX_TAGS = 8` までしか返さないため、推定結果に手動で 2 つ足せる余地を残す、という目安で決めている。実データの分布を見て調整する前提のため、変更が 1 箇所で完結するよう定数化した。

> なお、この上限の当初の根拠は「タグごとにインデックスを引くため、クエリ回数を抑える」というものだった（DynamoDB 時代）。D1 移行後は `inArray` の 1 クエリで引くため**その根拠は失効している**。上記は現行実装に即して立て直したものである。

**担保する場所**

| 層 | 実装 | 役割 |
|---|---|---|
| バックエンド | `createCardSchema` の `.max(MAX_TAGS_PER_CARD)` | **実効的な制限**。API を直接叩かれても超えられない |
| フロントエンド | `TagInput` の `max`、推定結果のマージ時の打ち切り | 弾かれる前に UI 側で止める |

以前はフロントエンドにしか制限が無く、API を直接呼べば無制限にタグを付けられた。上限に目的を持たせる以上、サーバ側で担保する。

### 却下した案

| 案 | 却下理由 |
|---|---|
| 画像埋め込み（外部 CLIP API） | 目的（商品の同定）に対して「見た目の類似」がずれる。外部ベンダー依存も増える |
| 画像埋め込み（Containers で CPU 推論） | 同上に加え、Containers がベータでオートスケールが無く、検索時にコールドスタート 2〜3 秒が直撃する |
| 画像埋め込み（Workers 内で ONNX 推論） | 同上に加え、128MB のメモリにモデル・ランタイム・画素バッファを収める必要があり、画像デコーダを WASM で自前調達する難度が高い |
| カード全体をベクトル化した検索 | 「タグが◯件一致」という既存マッチングの中核と整合しない |
| タグ推定の完全非同期化（Queue） | ユーザーがタグを確認・編集できなくなり、LLM の誤推定がそのまま登録される |

## Consequences

### Positive

- 写真を撮るだけでタグ候補が埋まり、カード登録の心理的コストが下がる。タグの網羅性が上がればマッチング成立率の向上が期待できる
- LLM がカテゴリ付きで返すため、ユーザーが自由入力するより表記が揃いやすい
- 推定結果は候補に留まり、ユーザーの確認を挟むため、AI の誤りがそのままデータに入らない
- フェーズ2 で Vectorize を導入しても、`MatchingEngine` と `CycleFinder` には一切変更が及ばない
- タグを埋め込む方式のため、カード数が増えてもベクトル数と埋め込みコストが比例して増えない

### Negative

- ビジョンLLM の推論コストが、写真つきカード登録のたびに発生する
- 11B モデルのため応答に時間がかかる。UI 側の工夫で体感を抑えているが、推定完了前にユーザーが登録を完了させた場合、その結果は破棄される
- LLM がニッチな作品・キャラクターを誤認する可能性がある。ユーザーが誤りに気づかず登録すると、誤ったタグでマッチングされる
- 楽観的 UI により状態遷移が複雑になった。`AbortController` の世代判定を `try` / `catch` / `finally` の3箇所すべてに置く必要があり、いずれかを落とすと「スピナーが消えない」「古いエラーが残る」といった不具合になる
- （フェーズ2）Vectorize のインデックスは次元・メトリックが不変のため、埋め込みモデルを変更する際は新規インデックスを作成して全タグを再投入する移行作業が必要になる
- （フェーズ2）書き込み反映に 5〜10 秒かかるため、タグを新規作成した直後にそのタグで検索してもヒットしない時間帯が生じる
