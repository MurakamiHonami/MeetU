# ADR-001: システムアーキテクチャと技術選定

## Background

本システムでは、通常のユーザー・投稿管理に加えて、複数ユーザー間でのN:N交換を実現する必要がある。

N:N交換では、単純なCRUDだけではなく、交換条件の判定やマッチングなどの複雑なビジネスロジックを扱う必要がある。

また、可能な限りCloudflareのサービス内でシステムを構成し、インフラストラクチャの複雑性を抑える。

## Decision

### 言語

TypeScriptを採用する。

Cloudflare Workersを中心とした構成とし、フロントエンド・バックエンドをTypeScriptで統一することで、Cloudflare上で一貫した開発環境を構築する。

N:N交換のマッチング処理については、処理量が増大した場合にTypeScriptでは性能上の問題が発生する可能性がある。

その場合は、マッチング処理をRustで実装し、別の計算基盤へ分離することを検討する。

### データベース

#### D1

ユーザー、投稿、交換情報などの主要な永続データをD1で管理する。

Cloudflare Workersとの統合が容易であり、システム全体をCloudflare内で構成できるため採用する。

#### KV

トレンド情報など、読み取り頻度が高く、多少の陳腐化を許容できるデータを保存する。

トレンド情報はリクエストごとに集計するのではなく、Cron Triggerから定期的に集計処理を実行し、その結果をKVに保存する。

#### R2

投稿画像やDMの添付ファイルなど、オブジェクトデータを保存する。

### ソフトウェアアーキテクチャ

#### Domain-Driven Design

DDDを採用する。

特にN:N交換では、交換条件、マッチング、交換成立などの複雑なビジネスルールを扱う必要がある。

これらのルールをドメインモデルとして明示的に表現し、UIやデータベースなどの技術的詳細から分離する。

#### Clean Architecture

Clean Architectureを採用し、ドメインロジックがD1などの具体的なインフラストラクチャに直接依存しない構成とする。

これにより、ビジネスロジックをDBやフレームワークから独立してテストしやすくする。

### ライブラリ選定

フロントエンド・バックエンドとも TypeScript で統一し、Cloudflare Workers 上で動作するライブラリを中心に選定する。

#### バックエンド（API / Workers）

| ライブラリ | 用途 | 選定理由 |
|-----------|------|----------|
| [Hono](https://hono.dev/) | HTTP ルーティング・ミドルウェア・RPC 型の源泉 | Workers 向けに軽量。`hono/jwt` で JWT 署名・検証も完結。ルート定義から `AppType` を export しフロントと型共有 |
| [Drizzle ORM](https://orm.drizzle.team/) | D1 への型安全なクエリ | SQLite 方言に対応。スキーマを TypeScript で定義し、マイグレーションと整合を取れる |
| [drizzle-kit](https://orm.drizzle.team/kit-docs/overview) | マイグレーション生成・検証 | `drizzle/` 配下の SQL を D1 に適用。CI で `db:verify` によりスキーマと migration の乖離を検知 |
| [Zod](https://zod.dev/) | リクエストボディ・クエリのバリデーション | 型推論とランタイム検証を一体で記述できる |
| [bcryptjs](https://github.com/dcodeIO/bcrypt.js) | パスワードハッシュ | Workers でも動作する純 JS 実装。`AuthService` で salt + hash を管理 |
| [ngeohash](https://github.com/sunng87/node-geohash) | ジオハッシュ計算 | 近くのカード検索（`NearbySearch`）で緯度経度を格子化 |

レイヤー構成は `domain/` → `usecase/` → `infrastructure/` → `interfaces/`（Hono ルート）の順で依存する。

#### フロントエンド（Web）

| ライブラリ | 用途 | 選定理由 |
|-----------|------|----------|
| [React](https://react.dev/) 19 | UI コンポーネント | 既存フロント資産との親和性。Hooks ベースで画面を構成 |
| [Next.js](https://nextjs.org/) 16（Pages Router） | ビルド・ルーティング | `output: "export"` で静的書き出しし、Cloudflare Workers Static Assets に配信。`pages/` ベースのファイルルーティングと `next/link` を使用（React Router は不使用）。全画面認証必須のため中身は CSR で描画し、`APP_ENV` で staging / production の `.env` を切り替える |
| [Hono RPC Client](https://hono.dev/docs/guides/rpc) (`hono/client`) | 型安全な API クライアント | バックエンドの `AppType` を `hc<AppType>` に渡し、パス・メソッド・パラメータをコンパイル時に検証 |
| [MUI](https://mui.com/) + [Emotion](https://emotion.sh/) | UI コンポーネント・スタイリング | フォーム・レイアウト・アイコンを統一。カスタム CSS と併用 |
| [Leaflet](https://leafletjs.com/) | 地図表示 | 近くのカード（Nearby）画面でマーカー表示 |

本番・ステージングの静的ファイルは **Cloudflare Workers Static Assets**（`wrangler.*.json` の `assets`）で配信する。Pages ではなく Worker にバンドルし、カスタムドメインを直接 Worker に紐づける。未知の動的パスは wrangler の `not_found_handling: single-page-application` が `index.html` へフォールバックする。

> Vite / React Router を用いた構成からの移行の経緯は issue #118 を参照。

#### フロントエンド・バックエンド間の API 契約（Hono RPC）

OpenAPI や手書きの fetch ラッパーではなく、**Hono RPC** で API 契約を TypeScript の型として共有する。

```
backend/src/index.ts          export type AppType = typeof app
        ↓ 型 import（実行時バンドルには含めない）
frontend/src/shared/api/client.ts   hc<AppType>(API_BASE)
frontend/src/features/*/api.ts      各ユースケースの RPC 呼び出し
```

| 側 | 実装 | 役割 |
|----|------|------|
| バックエンド | `Hono` インスタンスに `.route()` でルーターを連結し、`export type AppType = typeof app` | ルート・メソッド・入力の型定義の単一ソース |
| フロントエンド | `import { hc } from 'hono/client'` + `shared/api/client.ts` | `$get` / `$post` / `$url` でパスとクエリを型安全に呼び出し |
| フロントエンド | `features/*/api.ts` | 画面ユースケース単位の API。`entities/` の View 型を返す |

RPC クライアントは `authenticatedFetch` で `Authorization` ヘッダを付与し、`credentials: 'include'` で HttpOnly refresh Cookie を送る。401 時は `/api/auth/refresh` で access token を再取得してリトライする。R2 への直接 PUT など RPC 外の通信は `$url()` で URL だけ生成し、通常の `fetch` を使う。

**採用理由**

- バックエンドのルート変更がフロントのコンパイルエラーとして検知できる
- OpenAPI 生成・コード生成パイプラインが不要で、モノレポ内で完結する
- フロントは `hono` を devDependency 相当のクライアント用途のみで利用（バンドルサイズはクライアント部分のみ）

画面が参照する **View 型**（`Card`, `Owner`, `Match` 等）は `frontend/src/entities/` に置く。ドメイン型をそのまま露出させず、API レスポンス契約としてフロント側に表現する。

#### フロントエンド構成（バックエンド Bounded Context 準拠）

バックエンドの DDD に合わせ、フロントは **ビジネスルールを持たず**、モジュール境界だけを揃える。

```
frontend/src/
  app/           # ルーティング・認可ガード
  pages/         # ルート単位の薄い組み立て
  widgets/       # 複合 UI（SwipeDeck, CardItem, chat/* など）
  features/      # backend usecase 相当の API 呼び出し（auth, card, match, feed …）
  entities/      # View Model（Card, Match, Owner など）
  shared/        # api client, auth, device ユーティリティ
```

| フロント | バックエンド | 責務 |
|----------|-------------|------|
| `entities/*` | `domain/*` の表示モデル | 型定義のみ。マッチングロジックは持たない |
| `features/*/api.ts` | `usecase/*` + `interfaces/routes/*` | 画面ユースケース単位の API 呼び出し |
| `shared/api` | `interfaces/`（Hono RPC クライアント） | 認証付き fetch、HttpOnly Cookie 連携 |
| `pages/`, `widgets/` | — | プレゼンテーション。`pages` はルートと URL パラメータのみ、`widgets` に UI と状態（例: `widgets/chat/MatchChatThread`） |

`features/api.ts` は既存ページ互換の集約オブジェクト。新規コードは `features/card/api` など feature 直 import を推奨。

#### 認証

| 方式 | 実装 | 備考 |
|------|------|------|
| JWT（アクセストークン） | `hono/jwt` の `sign` / `verify` | TTL 1 時間。フロントはメモリ保持 + `Authorization: Bearer` |
| リフレッシュトークン | KV + **HttpOnly Cookie** | TTL 45 日。JSON には含めず `Set-Cookie` のみ。`/api/auth/refresh` でローテーション |
| セッション復元 | フロント `ensureSession()` | ページリロード時に Cookie 経由で refresh → 新 access token 取得 |
| 401 リトライ | `authenticatedFetch` | access 失効時に自動 refresh して1回リトライ |
| CORS | `credentials: true` + 許可オリジン列挙 | Web / API が別オリジンのため `SameSite=None; Secure`（本番・staging） |
| パスワード | bcryptjs（ラウンド 10） | メール + パスワードのサインアップ／ログイン |

`JWT_SECRET` は本番では Wrangler secret（初回またはローテーション時に手動設定）。ローカルは `backend/.dev.vars` を使用する。

## Consequences

### Positive

- Cloudflareを中心としたシンプルなインフラ構成になる
- TypeScriptでフロントエンドとバックエンドを統一できる
- Hono RPC により API 契約を型で共有でき、ルート変更の取りこぼしを減らせる
- N:N交換のビジネスロジックをドメインモデルとして管理できる
- DBやCloudflare APIへの依存を分離することで、ドメインロジックをテストしやすくなる
- トレンド集計をキャッシュすることで、通常のリクエストで集計処理を実行する必要がなくなる

### Negative

- DDD + Clean Architectureによって、単純なCRUDと比較して実装量が増える
- D1/KV/R2などCloudflare固有サービスへの依存が発生する
- N:N交換の処理量が増大した場合、マッチング処理を別サービスへ分離する必要が生じる可能性がある
